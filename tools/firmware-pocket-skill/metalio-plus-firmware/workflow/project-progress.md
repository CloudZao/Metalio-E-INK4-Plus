# 推进与证据

在独立WORK保持小型状态记录：需求/已确认UI、选中能力与版本、工程与环境路径、当前阶段、真实阻塞、下一步、证据文件。用scripts/record_progress.py或等价可读记录。阶段由任务决定，不强制M1-M7或固定BIN数量。

推荐顺序：必要需求/UI与架构 → 最小硬件/环境验证 → 真实能力单元 → 组合业务 → 双模式与真机反馈 → 交付。已验证可复用环境不重复安装；每次组合重新检查受影响行为。

进程活着不证明有进展；日志为空也不证明缓冲。结合日志增量、退出状态、.ninja_log时间/新增任务、当前编译子进程、CPU增量定位；旧.ninja_log总行数不是本次完成数。持续停滞先取证并测试最小复现，按项目PID树停止，不能全局杀所有ninja/python。PowerShell以原生命令退出码判断成功，stderr提示不自动等于失败。

计时分开：下载、环境准备、需求/UI、实现构建、返修、真机与人工等待；总墙钟时间另列，重试不可抹掉。记录冷/热环境、是否延续会话、模型/工具可见版本；Token无法读取写null，不估算成事实。基线/新版用同任务同材料且独立工作目录/上下文，测试是用户组织的，不自动读取00或其他版本。

材料阶段保存本轮计划和获取报告：为何选这些资源、哪些由02/缓存复用、哪些联网取得、原站和实际端点、版本/SHA与失败分类。安装Skill不要求工具齐全；网络访问阻塞、源404、证书、文件校验、本地权限分别说明，不把下载问题算成设备或业务功能失败。首个必要资源未取得时收敛，未尝试项不能报作已证实失败；保留可验证的断点缓存供续接。

轻量经验只写WORK：症状→适用设备/版本→证据→已验证修法→未验证限制。只保留可复用结论和必要工具结果，不要求隐藏思维链，不把猜测包装成根因。保存第一现场及后续修复，禁止覆盖唯一失败BIN或伪造“首轮成功”。
